## 1. 개요 / 목표

### v1.0의 목표

현재 Mock 모드(localStorage) 기반의 v0.9.1을 **Firestore/Functions/FCM 기반으로 완전히 전환**하여, 실제 매장 운영에 사용할 수 있는 프로덕션 버전으로 업그레이드한다.

**핵심 목표**:
- **데이터 영속성**: localStorage → Firestore 전환으로 브라우저/기기 간 데이터 동기화
- **실시간 동기화**: Firestore 리스너 기반 실시간 주문 상태 업데이트
- **백엔드 로직**: 주문 처리/포인트 적립 등 트랜잭션을 Cloud Functions로 이동
- **푸시 알림**: FCM 기반 주문 알림/배달 추적 알림 구현
- **이미지 저장**: Base64/localStorage → Firebase Storage 전환

### 비목표 (Non-goals)

v1.0 범위 밖인 기능:
- **멀티테넌트**: 단일 매장 기준 설계 (추후 확장 가능한 구조로 설계)
- **복잡한 정산/정기결제**: 기본 결제(현금/카드)만 지원
- **배달 플랫폼 연동**: 배달 대행사 API 연동은 v1.1 이후
- **관리자 웹앱 분리**: 현재 PWA 내 관리자 페이지 유지
- **멀티 스토어 관리**: 단일 스토어 기준, 추후 확장 가능한 구조

## 2. 아키텍처 개요 (v1.0)

### 사용할 Firebase 서비스 목록

| 서비스 | 용도 | 우선순위 |
|--------|------|---------|
| **Authentication** | 이메일/비밀번호 로그인, 관리자 인증 | 필수 |
| **Firestore** | 모든 비즈니스 데이터 저장 (주문, 메뉴, 리뷰 등) | 필수 |
| **Storage** | 메뉴 이미지, 리뷰 사진 저장 | 필수 |
| **Cloud Functions** | 주문 처리, 포인트 적립/차감, 푸시 알림 트리거 | 필수 |
| **FCM** | 주문 알림, 배달 추적 알림, 프로모션 알림 | 필수 |
| **Analytics** | 사용자 행동 분석 (선택) | 선택 |

### v0.9.1 vs v1.0 구조 비교

**v0.9.1 (현재 - Mock 모드)**:
```
클라이언트 (PWA)
  ↓
localStorage (브라우저 저장소)
  - 모든 데이터가 클라이언트에만 저장
  - 기기 간 동기화 불가
  - 브라우저 캐시 삭제 시 데이터 손실
```

**v1.0 (목표 - Firebase 연동)**:
```
클라이언트 (PWA)
  ↓
Firebase SDK
  ↓
┌─────────────────────────────────────┐
│ Firebase 서비스                      │
│  - Authentication: 로그인 관리        │
│  - Firestore: 비즈니스 데이터 저장    │
│  - Storage: 이미지 파일 저장          │
│  - Functions: 서버 로직 실행          │
│  - FCM: 푸시 알림 발송                │
└─────────────────────────────────────┘
```

**핵심 차이점**:
- **데이터 저장 위치**: localStorage → Firestore (클라우드)
- **동기화**: 수동 동기화 불가 → 자동 실시간 동기화
- **백엔드 로직**: 클라이언트 실행 → Cloud Functions 실행
- **이미지 저장**: Base64 문자열 → Firebase Storage URL
- **푸시 알림**: Mock 시뮬레이션 → 실제 FCM 발송

## 3. Firestore 스키마 설계(초안)

### 단일 매장 기준 컬렉션 구조

```
stores/{storeId}                           # 매장 기본 정보
  ├── menus/{menuId}                       # 메뉴 정보
  ├── categories/{categoryId}              # 카테고리 정보
  ├── orders/{orderId}                     # 주문 정보
  ├── reviews/{reviewId}                   # 리뷰 정보
  ├── coupons/{couponId}                   # 쿠폰 정보
  ├── pointsTransactions/{txId}            # 포인트 거래 내역
  ├── notices/{noticeId}                   # 공지사항
  └── fcmTokens/{userId}                   # FCM 토큰 (선택적)

users/{userId}                             # 사용자 프로필 (전역)
pointsBalances/{userId}                    # 포인트 잔액 (전역)
```

    open: string;                     // "09:00"

  deliveryAvailable: boolean;         // 배달 가능 여부

## 4. API 레이어 전환 전략

### 현재 구조 분석

현재 `src/lib/*.api.ts` 파일들은 다음과 같은 패턴을 따름:

```typescript
// 예: src/lib/orders.api.ts
export async function createOrder(payload: CreateOrderPayload): Promise<Order> {
  if (!USE_FIREBASE) {
    // Mock 모드: localStorage 기반 repository 사용
    return await ordersRepository.createOrder(payload);
  }
  
  // Firebase 모드: Firestore에 주문 문서 생성
  try {
    // ... Firestore 코드
  } catch (error) {
    // ... 에러 처리
  }
}
```

### 전환 전략 제안

#### 옵션 A: 현재 구조 유지 (추천)

**장점**:
- 기존 코드 구조 최소 변경
- Mock ↔ Firebase 전환 용이 (회귀 테스트 용이)
- 단계적 마이그레이션 가능

**단점**:
- 파일 내부가 길어질 수 있음
- Mock 코드와 Firebase 코드가 섞임

**구조**:
```
src/lib/
  ├── orders.api.ts              # Mock + Firebase 분기
  ├── menus.api.ts               # Mock + Firebase 분기
  ├── points.api.ts              # 이미 구현됨 (Mock + Firebase 분기)
  └── ...
```

#### 옵션 B: 파일 분리 (대규모 리팩토링)

**장점**:
- Mock 코드와 Firebase 코드 명확히 분리
- 유지보수 용이

**단점**:
- 대규모 리팩토링 필요
- 중복 코드 발생 가능성

**구조**:
```
src/lib/
  ├── orders.api.ts              # 공통 인터페이스
  ├── orders.api.mock.ts         # Mock 구현
  ├── orders.api.firebase.ts     # Firebase 구현
  └── ...
```

#### 예시 3: `getPointsBalance` / `spendPoints`

**v1.0 Firestore 구현**:
```typescript
// Firebase 모드
// 잔액 조회
const balanceDoc = await getDoc(doc(db, 'pointsBalances', userId));
return balanceDoc.exists() ? balanceDoc.data().balance : 0;

// 포인트 사용 (트랜잭션 필수)
await runTransaction(db, async (transaction) => {
  const balanceRef = doc(db, 'pointsBalances', userId);
  const balanceDoc = await transaction.get(balanceRef);
  const currentBalance = balanceDoc.exists() ? balanceDoc.data().balance : 0;
  
  if (currentBalance < amount) {
    throw new Error('포인트 잔액이 부족합니다');
  }
  
  // 잔액 차감
  transaction.update(balanceRef, {
    balance: currentBalance - amount,
    totalSpent: (balanceDoc.data()?.totalSpent || 0) + amount,
    updatedAt: serverTimestamp(),
  });
  
  // 거래 내역 추가
  const txRef = doc(collection(db, 'stores', storeId, 'pointsTransactions'));
  transaction.set(txRef, {
    userId,
    type: 'spend',
    amount: -amount,
    ref: { kind: 'order', id: orderId },
    note: '주문 포인트 사용',
    at: serverTimestamp(),
  });
});
```

**구현 포인트**:
- 포인트 사용은 **트랜잭션 필수** (동시성 제어)
- 잔액(`pointsBalances`)과 거래 내역(`pointsTransactions`) 원자적으로 업데이트

## 5. Cloud Functions / 백엔드 로직

### v1.0에서 Functions로 이동해야 할 로직

#### 1. 주문 생성 시 트랜잭션 처리

**왜 Functions에서 해야 하는가**:
- 주문 생성 시 포인트 적립, 쿠폰 사용 처리, 재고 차감 등 여러 작업을 **원자적으로 처리**해야 함
- 클라이언트에서 직접 처리하면 네트워크 지연/실패 시 데이터 불일치 발생 가능
- Firestore 트랜잭션은 Functions 환경에서 더 안정적

**구현 내용**:
- 주문 문서 생성 → 포인트 적립 거래 추가 → 쿠폰 사용 처리 → 잔액 업데이트 (원자적)
- 실패 시 롤백

---

#### 2. 주문 상태 변경 시 포인트 적립/차감

**왜 Functions에서 해야 하는가**:
- 주문 완료 시 포인트 적립, 주문 취소 시 포인트 환불 등 **비즈니스 로직의 일관성** 보장
- 관리자가 주문 상태를 변경할 때도 자동으로 포인트 처리

**구현 내용**:
- Firestore `orders/{orderId}` 업데이트 트리거 (`onUpdate`)
- 상태가 `completed`로 변경 시 포인트 적립
- 상태가 `cancelled`로 변경 시 포인트 환불/차감

---

#### 3. FCM 푸시 알림 발송 (주문 상태 알림 등)

**왜 Functions에서 해야 하는가**:
- FCM 서버 키를 클라이언트에 노출하면 안 됨 (보안)
- 주문 상태 변경 시 자동 알림 발송 (트리거 기반)

**구현 내용**:
- 주문 상태 변경 시 (`onUpdate`) → FCM 토큰 조회 → 푸시 알림 발송
- 알림 타입: 주문 접수, 조리 시작, 배달 시작, 완료, 취소 등

---

#### 4. 포인트 만료 처리 (스케줄러)

**왜 Functions에서 해야 하는가**:
- 매일 자정에 만료된 포인트를 자동 처리해야 함
- 클라이언트에서 실행 불가 (사용자가 앱을 안 켜면 미실행)

**구현 내용**:
- Cloud Scheduler + Cloud Function (매일 00:00 UTC 실행)
- `pointsTransactions`에서 만료일이 지난 적립 포인트 찾기 → 만료 거래 추가 → 잔액 차감

---

#### 5. (선택) 매장 휴무/영업시간 스케줄러

**왜 Functions에서 해야 하는가**:
- 매일 자정에 영업 상태 업데이트 (휴무일 체크)
- 클라이언트에서 실행 불가

**구현 내용**:
- Cloud Scheduler + Cloud Function (매일 00:00 KST 실행)
- `stores/{storeId}`의 `businessHours` 확인 → `isOpen` 업데이트

---

#### 6. 이미지 최적화 (선택)

**왜 Functions에서 해야 하는가**:
- 업로드된 이미지를 자동 리사이징/최적화하여 Storage 용량 절약
- 클라이언트에서 처리하면 처리 시간 증가

**구현 내용**:
- Storage 업로드 트리거 (`onFinalize`) → 이미지 리사이징 → 원본 삭제 (선택)
