## 1. 개요
S01 단계에서는 주문 플로우 관련 라우트, 컴포넌트, 저장소(localStorage), 기존 E2E 스펙 구조 및 사용 가능한 셀렉터를 전수 조사하였다. 목표는 S02 이후 구현 시 셀렉터/플로우 불확실성을 제거하고, 최소 수정으로 안정적인 시나리오를 확립하는 것이다.

## 2. 테스트 목표 (Mock 모드, 결제 OFF)
1) 고객: 로그인 → 메뉴 선택 → 장바구니 → Checkout → 주문 생성(결제 없이 확정) → 주문내역 등장 확인.
2) 관리자: 별도 컨텍스트 로그인(로컬스토리지 주입) → `/admin/orders` 접근 → 방금 생성된 주문 행 존재 및 상태(`placed`/`pending`) 확인.
3) 교차 검증: 고객 측 OrderHistory와 관리자 측 Orders 테이블이 동일한 `orderId` 를 공유하는지.

## 3. 실행 환경 요약
- Playwright 설정: `src/playwright.config.ts` / baseURL `http://localhost:3000` / `pnpm dev` 로 서버 구동.
- 브라우저 프로젝트: chromium, firefox, webkit, Mobile Chrome, Mobile Safari (우선 안정성 위해 chromium 단일 사용 후 확대).

## 5. 주문 생성 시퀀스 (Mock)
1. 고객 로그인 (localStorage 기반 세션 세팅됨).
2. 메뉴 페이지 이동 후 첫 메뉴 상세 진입 또는 카드에서 바로 담기.
3. "장바구니 담기" → `/cart` 이동 (혹은 메뉴에서 장바구니 버튼 클릭 후 자동 이동 처리). 
4. `/checkout` 이동 → 결제 OFF 모드이므로 결제 API 없이 `ordersRepository.createOrder` 실행.
5. 성공 시 Toast/Alert (텍스트: "주문이 접수되었습니다" 등) + `/order-history` 혹은 `/order/ORDxxxx` 리다이렉트.
6. `orders` localStorage 갱신 → 관리자 페이지에서 `listOrdersByStore` 병합 조회 → 최신 행 노출.

## 7. 셀렉터 매핑 & 개선안
현재 다수 셀렉터가 텍스트 기반(`button:has-text()`)으로 구성되어 변경/번역 시 취약. 안정화를 위해 data-testid 추가 권장.

| 영역 | 현재/가능 셀렉터 | 권장 신규 `data-testid` | 이유 |
|------|------------------|------------------------|------|
| 메뉴 카드 | `a[href^="/menu/"]` | `menu-card` | 경로 변화/정렬 변경 대응 |
| 담기 버튼 | `button:has-text("담기")` | `add-to-cart` | 텍스트 변경 무관 |
| 장바구니 아이템 | `.cart-item` | `cart-item` | 클래스 리팩토링 대비 |
| Checkout 확정 | `button:has-text("주문")` | `confirm-order` | 다국어/문구 수정 대비 |
| 주문내역 행 | `.order-item` | `order-item` | 스타일/구조 변경 대응 |
| 주문 상태 배지 | `text=주문접수` 등 | `order-status-badge` | 상태 텍스트 포맷 변경 대비 |
| 관리자 주문 행 | 추정 `[data-row]` | `admin-order-row` | 시나리오 명확화 |
| 관리자 필터 바 | `form` | `admin-orders-filter` | 필터 기능 자동화 예정 |

초기 구현(S02~S04)에서는 기존 셀렉터 활용 후 플래키 발생 시 S05에서 단계적 도입.

## S03 – 고객 주문 생성 플로우 구현 (happy path)
